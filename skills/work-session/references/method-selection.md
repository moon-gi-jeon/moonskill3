# 핵심 방법과 제한 시간의 선택

최적화·배정·분류·복잡한 판정 등 방법 선택이 실제 결과를 바꿀 때만 읽는다. 특정 문제·솔버·포트·모델을 전제하지 않는다.

## [모델과 성공 기준]

결정할 것, 입력 의미/기간/단위, 반드시 지킬 조건, 비교할 목표·방향·우선순위, 사용자에게 위임된 절충과 미확인을 구별한다. 순서가 빠른 구현과 성공한 결과는 다르다. 제약을 빼거나 몰래 가중치를 정해 문제를 쉽게 만들지 않는다.

## [후보·가능해·최적성]

- 이 흐름의 후보는 같은 전체 필수제약·요구조건을 모두 지키는 서로 다른 가능해 후보다. 단순히 방법 이름만 세 개 적거나 조건을 빼서 쉬운 후보를 만들지 않는다. 초기 설계 제안과 실제 검증된 가능해의 상태/근거는 구별한다.
- 기본 비교 폭은 세 개지만 시간·자료·명확한 우위 때문에 둘 등으로 좁힐 수 있다. 억지로 세 번째를 만들어 시간을 낭비하지 않는다. 실제 검토한 수·탈락/축소 이유·남은 비교 범위를 남긴다.
- 승인된 작은 실험에서는 각 결과의 동일 필수조건 충족을 먼저 확인한다. 제약을 어긴 결과는 탈락/수정 대상으로 기록하며 가능해 수에 넣지 않는다. 아직 구현하지 않은 서비스 요구는 설계의 준수 경로와 미검증 범위를 밝히고, 세 완성 앱을 만들지는 않는다.
- 그 뒤 합의한 기준으로 선정하는 단계가 이 흐름의 최적안 선정이다. 비교한 범위와 수치·선택 이유를 설명하고, 그 범위 밖에 더 나은 해가 없다는 수학적 보장은 별도 근거가 있을 때만 적는다.
- 증명된 최적해는 해당 모델의 정확한 구조적 해법, 유효한 전수 탐색/가지치기, 적합한 상·하한 일치 등 근거가 필요하다. 허용 오차가 있으면 그 보장 수준도 적는다.
- 시간초과/미발견은 불가능성 증명이 아니다. 휴리스틱 결과를 전역 최적이라고 부르지 않는다. 필수조건이 최적성 증명을 요구하면 미증명 상태를 충족으로 바꾸지 않는다.

## [총 작업 비용]

후보마다 보장 수준·품질 확인법뿐 아니라 모델링/작은 실험, 구현, 서비스/UI/API 통합, 검증, 사용자 설명·문서, 제출 준비의 비용과 실패 위험을 함께 비교한다. 어려운 방법의 이론적 결과가 좋아도 전체 필수 흐름을 완성할 시간이 없는 경우 대안을 제안한다.

시간은 실제 확인한 마감·현재 시간·남은 허용 작업 시간을 사용한다. 추정 작업량은 범위와 불확실성을 밝히고 관측 후 갱신한다. 후속 AI 금지 시간을 구현 시간으로 빌리지 않는다. 모든 과제에 똑같은 분 단위 시간표·effort 변경·고정 벤치마크 수를 강제하지 않는다.

실험 전에 중단/전환 신호를 제안한다. 예: 상태 수가 예측 범위를 벗어남, 제공 도구 부재, 실제 지연, 검증하기 어려운 핵심 조건. 검증된 현재 결과는 보존하고, 중요한 방법·보장·범위 변경은 이유와 영향을 설명해 실제 결정을 받는다. 일상적인 버그 수정 때문에 전체 후보 실험을 반복하지 않는다.

## [구현 전 비교의 목적과 정량 근거]

첫 전체 구현 전에 서로 다른 가능성을 충분히 고민해 불필요한 핵심 알고리즘 롤백을 줄이고, 선택의 타당성을 사용자가 이해할 근거를 확보한다. 이후 실제 오류/새 요구/더 나은 근거가 생겼을 때 합당한 변경까지 막는 것은 아니다.

같은 입력·기간·필수조건·비교 기준에서 실제 지표/단위, 필수조건 검사 결과, 기준선과 차이, 계산/실행 시간 등 관련 수치를 기록한다. 측정값과 구현 비용 추정을 섞지 않는다. 수치가 없으면 미측정과 이유를 밝히며 알고리즘 이름이나 임의 점수만으로 우위를 선언하지 않는다. 선택 이유·버린 안·한계와 근거 V-ID는 이해 문서의 상세 설명과 상단 항목별 요약에도 연결한다.

## [품질과 서비스 확인]

결과를 원문 제약·단위로 다시 검사하고 중요한 목표값은 별도 계산한다. 가능한 작은 사례의 수기/전수 기대값과 비교한다. 유효한 bound/gap을 쓸 때에는 같은 모델·단위·방향인지 확인하고 0 분모나 불가능한 기준선을 비율 비교에 쓰지 않는다. 관련 없는 수학 용어를 꾸미기 위해 넣지 않는다.

실제 입력→방법→결과가 제공 환경의 필요한 API/화면/파일로 이어지는지도 확인한다. 작은 코어 성공과 전체 서비스 완성을 구별하고, 선택 이유·미충족 보장·한계·전환 근거를 PLAN/DECISIONS/REVIEW와 이해 문서에 연결한다.
