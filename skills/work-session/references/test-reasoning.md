# 중요한 검증을 설계하고 설명하기

자료의 수치·핵심 알고리즘·상태 변경 등 실패 영향이 큰 동작을 검증할 때 읽는다. 고정 프레임워크나 전부 TDD를 요구하는 지침이 아니다.

## [검사 전]

무슨 요구를 지키는지, 어떤 틀린 구현을 잡아야 하는지, 어떤 입력/상태에서 무엇이 나와야 하는지 먼저 적는다. 기대값은 원문·실제 답·합의 기준과 별도 계산에 근거한다. 결과를 본 뒤 기대를 맞춰 바꾸지 않는다.

관련 정상 흐름, 조건이 딱 맞거나 벗어나는 경계, 중요한 오류/변경 입력을 고른다. 모두에게 빈값·동시성·인증·최대값 검사를 강제하지 않는다. 실제 과제의 중요한 실패를 구별하는 최소 검사를 우선한다.

## [독립성]

생산 함수를 다시 호출해 기대와 결과를 동시에 만들면 독립 검산이 아니다. 작은 수기 예, 더 단순한 기준 구현/전수 열거, 원문 불변조건, 의미 있는 변경 입력 중 적절한 것을 사용한다. 공유한 파서·입력 해석·업무 가정이 있으면 그 한계를 밝힌다.

후보의 의견 일치·다른 에이전트의 PASS·테스트 개수는 독립 기대값의 타당성을 대신하지 않는다. 독립 리뷰의 발견도 실제 파일/재현/수정 후 검증과 연결한다.

## [실패 후]

실제 결과가 기대와 다르거나 원인 모를 중요한 실패가 있으면 diagnosing-bugs를 읽고 관찰→유용한 재현→구별할 가설→최소 수정→원래 실패와 관련 회귀 검사로 진행한다. 검사기의 기대값·환경 실패와 제품 결함도 구별한다. 같은 실패를 같은 조건으로 반복하지 않는다.

## [기록과 사용자의 이해]

REVIEW에는 사유, 실제 방법, 기대값 출처/왜 신뢰 가능한지, 명령/입력/관측 결과, 확인한 범위/못 밝힌 점, 변경 영향을 적는다. 앞의 현재 검증 카드와 PROJECT_GUIDE에는 쉬운 말로 핵심 이유와 결과를 해설하고 V-ID를 연결한다. ‘전수 검산’ 같은 말만 쓰지 말고 무엇을 어떻게 따로 셌는지 설명한다.

변경된 코드/입력/조건의 영향 범위만 재검증한다. 문장 정리만으로 기능 검증 전체를 무효화하지 않으며, 문서 변경은 실제 내용·숫자·링크의 일치를 확인한다. 미검증/사람 확인/오래된 근거를 통과와 구별한다.
