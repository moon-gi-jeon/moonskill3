# 문서와 결정 기록

Addy Osmani의 documentation-and-adrs를 이 패키지의 경량 문서 운영에 맞게 조정한 수정본이다. 원문 커밋·변경 내역은 루트 SOURCES와 manifest에, MIT 고지는 LICENSE.upstream.txt에 보존한다.

## 기존 관례와 독자의 목표를 먼저 확인

같은 역할의 문서·제목·ID·경로·출처와 과제 지정 양식을 먼저 읽고 재사용한다. work-session이 이미 PLAN/DECISIONS/REVIEW를 정본으로 쓰면 새 ADR 폴더·결정별 파일·CHANGELOG·별도 worklog를 강제하지 않는다. 원문 과제 README를 작업 기록으로 덮어쓰지 않는다.

PLAN과 협의 내용을 자동 갱신하는 데 별도 목차 승인을 반복하지 않는다. 승인된 범위를 벗어나는 중요한 내용 변경만 실제 결정 절차로 돌린다. 문서를 잘 꾸미는 것이 사실 확인·구현 승인·실제 검증을 대신하지 않는다.

직접 작성·관리하는 문서는 상단에 짧은 `[문서 역할]`과 관련 정본/실제 확인 위치를 둔다. PLAN은 현재 마스터, DECISIONS는 중요한 실제 선택, REVIEW는 상세 검증, PROJECT_GUIDE은 실제 결과의 해설임을 구별한다. 사용법·협업·조건부 인계 문서도 실제 목적을 밝힌다. 없는 문서는 미작성/예정으로 표시한다. 지정 양식이 우선이며 제공 원문·데이터·라이선스를 수정하거나 빈 파일을 새로 만들지 않는다.

## 의미를 지키며 관련 부분만 정리

1. 편집 전에 보존해야 할 요구·Q/U·실제 답·수치·단위·날짜·명령·경로·조건·가정·불확실성·한계를 식별한다.
2. 새 정보는 해당 절에 넣고 현재 상태·다음 행동을 상단에서 찾게 한다. 주제마다 맨 아래에 추가하거나 매 명령 후 전체 문서를 재작성하지 않는다.
3. 짧은 제목·라벨·목록·세로 항목을 활용한다. 좁은 IDE에서 긴 가로 표를 읽게 하지 않는다. 짧게 만든다는 이유로 근거와 선택 이유를 없애지 않는다.
   길게 이어진 설명 행은 문장·의미 단위로 줄바꿈하되 명령·URL·식별자·지정 스키마를 자르지 않는다.
4. 폐기는 [drop] + 이유, 변경은 대체 ID/위치를 남긴다. 실제 선택·선택자/위임·이유·버린 대안·한계는 기존 DECISIONS 관례로 보존한다.
5. 근거 정본을 중복하지 않는다. PLAN은 현재 요구/계획과 검증 색인, REVIEW는 상세 검증, DECISIONS는 선택 이유다. 링크·상태가 서로 맞는지 확인한다.
6. 원문과 수정본을 비교해 의미·조건·불확실성의 소실을 복구하고 확인되지 않은 사실은 표시한다. 문체를 다듬으며 더 강한 보장이나 새 예시 수치를 만들지 않는다.

검토 중인 문서 형식은 `[현재 상태]`, `[필수조건]`, `[제약조건]`, `[요구기능]`, `[검증 색인]`처럼 괄호형 제목/짧은 세로 항목으로 탐색을 돕는다. 같은 조건은 R-ID 상세에 한 번만 정의하고 분류 절은 짧은 링크로 연결한다. 사용자 미결 선택에는 추천·근거/반례·영향·실제 답/선택·상태가 보이게 하고 답을 받으면 같은 항목을 갱신한다.

REVIEW 앞에는 사용자 관점의 현재 검증 카드(왜/방법/기대값 신뢰 근거/실제 결과/한계/V-ID)를, 뒤에는 상세 실행 이력을 둔다. 이해 문서에는 자세한 실제 설명과 상단 항목별 요약을 별개로 제공한다. 이력·상세를 줄이는 것이 문서 정리의 목표는 아니다. 새 D/V 상세 저장 뒤 PLAN 색인을 연결하고, 마무리 때 현재/과거·참조 존재·한국어·가독성을 확인한다.

승인 전 상세 설명은 PLAN의 관련 U/단계 ID에 두고, 필요한 경우에만 별도 X-ID로 구별한다. 추천·근거/조건·영향·이번 범위·실제 승인 상태를 함께 찾을 수 있게 한다. CLI의 짧은 설명에는 현재 추천과 중요한 영향·결정 범위를 남기고 정확한 PLAN ID로 연결한다. 설명을 다른 파일에 복제하거나 새 승인 절차를 만들지 않는다.

## 과제 지정 문서 작성

과제 원문에서 요구한 문서명·양식·문항을 PLAN의 제출물에 연결한다. 근거가 생기는 대로 승인 범위에서 자동으로 작성·갱신한다. PLAN에서 요구와 범위를, DECISIONS에서 실제 선택과 이유를, REVIEW에서 실행·결과·한계를 찾아 실제 파일과 대조한다. 독자가 필요한 결론과 핵심 근거를 본문에 정리하고, 과제에서 허용하는 경우 정확한 파일·절·ID로 상세를 연결한다. 정본의 이력과 로그를 그대로 옮길 필요는 없다. 최종 저장본과 과제 지정 항목을 대조한다.

## 사용자용 문서는 실제 사용을 안내

독자·목표·범위를 먼저 확인하되 이미 과제와 계획에 있으면 다시 묻지 않는다. 사용법, 기술 참조, 이해 설명과 내부 협업 기록의 목적을 구별한다.

사용법은 실제 준비→시작→제공 환경 접속→대표 작업→결과 확인→문제 대응 순서로 쓴다. 실제 실행 명령·필수 인증 여부·접속 경로를 현재 저장 파일 및 실행 결과와 대조한다. 한계를 숨기지 않되 미완료 토론이나 내부 작업 메모를 사용 절차 한가운데 넣지 않는다.

협업 기록은 실제 사건·의견·역할·변경·검증만 근거로 작성한다. 사용하지 않은 도구·허위 반론·가짜 실행을 만들어 채우지 않는다. 과제에 없는 문서 종류·분량·문항을 의무화하지 않는다.

외부 문서 플랫폼·패키지·교정 도구·추가 인증이 필요하지 않다. 작업 허용 단계와 제출 형식을 따르고 문서 변경분에 맞는 내용·경로 확인을 수행한다.
