# 실제 결과와 과정 이해

현재 PLAN·관련 DECISIONS·REVIEW·실제 코드/자료/결과를 대조한다. 가상의 이상적 해법이나 사용자 생각을 꾸며 쓰지 않는다. 없는 알고리즘·독립 리뷰·실행 근거를 만들어 설명하지 않는다.

## 적용 시점

중요 설계 선택 전후, 첫 결과 확인, 사용자 이해 요청, 허용된 마무리 준비에 필요한 부분만 적용한다. AI 사용이 금지되는 후속 단계에는 답변·초안 작성에 사용하지 않는다.

## 자유 양식 해설의 작성과 확인

처음 만들거나 구조를 고칠 때 [이해 문서 양식](assets/UNDERSTANDING.template.md)을 끝까지 확인한다. 길면 절 단위로 나누어 읽는다. 상단 예상 문항을 쓰거나 검사할 때는 양식의 `[예상 서술형 6문항 — 사전 복기]`부터 `[01 현재 결과와 과제 목적·성공 기준]` 직전까지 여섯 유형을 모두 읽는다. 앞부분에서 출력이 잘렸으면 다음 범위를 이어 읽는다.

- 예상 문항은 실제 과제에 맞춰 **대표 결과와 흐름, 방법·데이터 범위의 선택, 검증과 신뢰 근거, 입력 변화·오류의 동작, 한계·대안, 사용자의 질문·판단과 영향**을 설명한다. 관련 주제를 한 문항에 묶어도 된다. 실제 근거가 없는 사건이나 대안은 꾸미지 않는다.
- 문항마다 `[답변 핵심]` 2~3문장, `[기억 단서]` 2~3개, `[근거]`를 **각각 별도 목록 줄**에 둔다. 근거는 내용이 드러나는 제목과 실제 파일·절 또는 관련 ID로 표시한다. 예상 문항의 번호 외에 별도 ID를 붙일 필요는 없다.
- 마무리 전에 저장된 파일을 다시 읽고 **문항별 세 필드와 중요한 주제의 포함 여부**를 양식과 대조한다. 누락은 해당 문항만 보완한다. 문항 수나 제목 모양만으로 통과를 판단하지 않는다.
- 본문에서는 해당하는 `[판정 기준]`, `[검증 방법]`, `[신뢰 근거]`, `[한계]`, `[내 판단과 영향]`을 실제 근거와 연결한다. 상단의 같은 표현으로 본문 대조를 대신하지 않는다. 과제 지정 양식과 파일 제한을 우선한다.

## 설명할 핵심

- 실제 입력→주요 처리→출력과 사용자가 보는 결과를 작은 예로 설명.
- 핵심 방법이 실제로 어떤 규칙·기간·범위를 사용하며, 왜 선택했고 다른 후보의 손익은 무엇인지.
- 요구상 고정 조건, 사용자 절충, 확인 사실, 가정의 차이와 실제 선택 위치.
- 무엇이 어려웠고 어떤 의견·실패·수정이 결과를 바꿨는지. 없었던 반론이나 기여를 만들지 않음.
- 검증 기준·기대값의 출처, 방법의 타당성·독립성, 실제 결과와 미확인 범위.
- 한계·부작용·대안·실제로 사용한 대리지표의 가정과 영향. 자세한 근거는 REVIEW로 연결.
- 실제 파일/함수·문서 ID를 짚어 사용자가 다시 찾을 수 있게 설명.

간결한 상태 보고와 이해 설명을 구별한다. 사용자가 모르겠다고 하면 같은 요약을 반복하지 말고 대표 입력·두 후보 결과 차이·처리 순서 등 구체적 예로 바꾼다.

## 실제 프로젝트 이해 문서를 자동 유지

기본 제목은 **프로젝트 결과와 의사결정 해설**, 기본 파일명은 `PROJECT_GUIDE.md`다.
같은 역할의 기존 `UNDERSTANDING.md`나 과제 지정 문서가 있으면 재사용하고,
이미 연결된 파일을 강제로 이름 변경하거나 두 번째 해설 문서를 만들지 않는다.
제목/파일명 변경은 문서의 필수성·작성 시점·상세 설명과 상단 요약의 역할을 바꾸지 않는다.

사용자가 별도로 Skill 이름이나 저장 명령을 기억하지 않아도, 중요한 방법/설계 선택과 첫 실제 결과에서 `PROJECT_GUIDE.md` 또는 같은 역할의 기존 문서를 작성·갱신한다. 허용된 최종 마무리에서는 현재 제출본과 일치하는 설명이 있는지 반드시 확인한다. PLAN 마스터·DECISIONS 이력·REVIEW 근거는 그대로 유지한다.

이 문서는 사용자가 자기 과제를 충분히 이해하는 데 필요한 기본 산출물이다. 필요성을 다시 묻거나 후속 문항의 AI 답안 작성 계획으로 해석하지 않는다. 후보의 동일 필수조건 충족·실제 정량 비교·선정 이유와 한계를 자세히 설명하고, 문서 상단에 항목별 요약과 예상 서술형 6문항의 답변 핵심을 제공한다.

초기 자료·질문 정리만 하는 단계에는 빈 이해 문서를 미리 채우지 않는다. 실제 중요한 선택이나 첫 결과가 생긴 뒤 해당 절부터 작성한다. 계획만 있는 내용과 실제 구현된 내용을 구별한다.

같은 해설 파일의 영향을 받는 절을 갱신하고 기존 사실·근거·링크를 보존한다. 상단과 02의 대표 입력은 같은 실제 사례를 쓰고, 상단 복기 사례는 판단·달라진 동작·직접 확인 근거가 분명한 한 건을 고른다. 결과·흐름·모듈·기법·데이터/규칙·검증·장애·담당자·운영은 내용 누락을 대조하는 관점이다. 검증 방법은 실행·관측, 신뢰 근거는 기대값 출처와 구현과의 독립성, 한계는 검증한 범위를 설명한다. 처음 보는 사용자가 실제 작동·선택·검증의 타당성을 이해할 수 있게 쓰고, 원시 로그는 상세 정본에 연결한다.

문서 상단에 실제 결과/과정의 해설이라는 역할과 현재 PLAN·선택 DECISIONS·검증 REVIEW의 실제 경로/ID를 짧게 안내한다. 없는 문서를 존재하는 근거로 링크하지 않는다. 승인 전의 긴 추천/범위 설명은 PLAN의 해당 U/단계/필요한 X-ID를 재사용하고, 실제로 확정된 내용만 이 이해 문서에 반영한다.

과제의 목적·성공 기준, 주요 사용자 시나리오, 실제 핵심 처리/알고리즘과 선택 이유·버린 대안, 주요 검증의 사유/방법/신뢰 근거/결과/한계, 큰 수행 과정, 실제 어려움·경계조건·사용자 개입과 개선, 대안·대리지표 사용 여부를 포함한다. 없었던 알고리즘·실패·거절·대리지표를 서식을 채우려고 만들지 않는다. 중요한 수치·선택·현재 상태는 실제 파일과 Q/D/V-ID에 연결한다.

과제에서 AI 협업 질문·문서 양식을 지정했다면 원문 문항을 그대로 읽어 각 문항의 실제 사실·근거·관련 설명 위치를 정리한다. 이전 과제의 질문 수나 기억나는 주제를 새 과제의 정확한 원문이라고 추정하지 않는다. 별도 필수 제출 문서는 지정 이름/형식을 지키며 이해 문서로 대체하지 않는다. 출력 파일 제한이 있으면 허용된 동등 문서 안에 통합하고 실제 위치를 PLAN에 둔다.

실제 중요한 답·판단 변경·첫 결과·실패/개선·핵심 검증 뒤 영향받는 설명만 갱신한다. 새 반례나 재검증으로 설명 근거가 바뀌면 본문과 해당 상단 요약·문항을 같은 갱신에서 고친다. 결론 수치가 같아도 이유나 한계가 달라지면 반영하고 최신 D/V-ID를 연결한다. 최종 허용 단계에서는 저장한 문서에서 해당 본문 라벨과 직접 근거를 확인한다. 상단 문항의 수치·단위·횟수·간격·포함 경계는 실제 원문 및 적용한 R/V와 대조하고, 선정 이유·한계도 현재 코드·결과·D/V와 대조한다. 의미를 바꾸는 축약이 있으면 해당 줄을 바로잡는다. 매 명령마다 전체 파일을 다시 쓰거나 두 개의 이해 정본을 만들지 않는다.

본문은 링크를 열기 전에도 결과와 이유를 이해할 수 있게 쓰고, 상세 확인에는 PLAN·DECISIONS·REVIEW의 해당 위치를 연결한다. 수행 과정은 실제 사건 순서로 설명한다. 예상 질문은 사전 복기용으로 표시하고 후속 단계에는 해당 단계의 AI·자료 열람 규정을 적용한다.
