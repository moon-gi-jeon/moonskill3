# 프로젝트 결과와 의사결정 해설

[문서 역할] 실제 과제의 목적·방법·선정 근거·수행 과정·주요 검증·한계·사용자 개입의 상세 해설과 항목별 요약.
[다른 내용의 위치] 현재 요구/계획은 PLAN, 실제 선택 이력은 DECISIONS의 D-ID,
수치·실행·검증 방법/한계의 상세 정본은 REVIEW의 V-ID에서 확인한다.
실제 문서명·위치로 바꾸고 아직 없는 문서는 예정/미작성으로 구분한다.

기본 파일명은 `PROJECT_GUIDE.md`다. 같은 역할의 기존 문서나 과제 지정 이름이 있으면 재사용한다.

작성 지침: 실제 과제·현재 구현·정본 근거로 아래 항목을 설명한다. 빈 양식을 그대로 제출하지 않는다. 전문 용어는 실제 역할과 작은 입력/결과로 풀어 쓴다. 문서 상단에는 요약과 예상 서술형 6문항을 두고, 본문에서 결과를 상세히 설명한다. 같은 역할의 허용된 문서가 있으면 재사용한다.

## [항목별 요약 — 먼저 읽기]

과제 목적·현재 결과와 필수 요구 충족/미충족·입력에서 출력까지의 흐름·핵심 선택과 이유·검증의 결론과 신뢰 범위·한계·주요 사용자 판단을 짧게 정리한다. 링크를 열기 전에도 핵심 결과와 이유를 이해할 수 있게 쓰고, 상세 절과 실제 R/D/V-ID·파일로 연결한다.

## [예상 서술형 6문항과 답변 핵심 — 사전 복기]

아래 여섯 유형을 해당 프로젝트의 실제 요구·결과에 맞는 서로 다른 질문으로 구체화한다. 각 질문 바로 아래에 [답변 핵심] 2~3문장, [기억 단서] 2~3개, [근거] 실제 파일·절·ID를 둔다. 설명에 필요한 핵심 수치와 단위를 넣고, 전체 표·명령·로그는 정본에 연결한다. 아래 답변 포인트는 작성 기준이며, 완성 문서에는 해당 프로젝트의 사실로 채운다. 근거가 부족하면 확인한 범위와 남은 불확실성을 적는다. AI 사용이 허용된 개발·마무리 단계에서 작성하고, 후속 단계의 AI 사용 및 자료 열람은 실제 시험 규정을 따른다.

1. **무엇을 해결했고, 대표 입력 하나는 어떤 과정을 거쳐 어떤 결과가 되는가?**  
   답변 포인트는 사용자와 목표, 대표 입력 → 핵심 처리 → 실제 출력, 필수 결과의 상태다. 구현 위치와 관련 R-ID를 연결한다.
2. **왜 이 방법과 데이터 범위·기간을 선택했으며, 다른 후보와 비교하면 어떤 차이가 있었는가?**  
   답변 포인트는 합의한 기준, 선택을 좌우한 실제 비교값이나 근거, 버린 후보의 손익이다. 관련 D/V-ID를 연결한다.
3. **핵심 결과를 어떻게 검증했고, 기대값과 실제 결과를 왜 신뢰할 수 있는가?**  
   답변 포인트는 검사 입력과 방법, 기대값을 별도로 얻은 방식, 관측 결과와 검증 범위다. REVIEW의 V-ID를 연결한다.
4. **입력이나 조건이 바뀌면 어떤 결과가 다시 계산되고, 올바르게 바뀌는지 어떻게 확인했는가?**  
   답변 포인트는 변경 전후 입력·출력 한 쌍, 다시 계산하는 범위, 변경 후 검사와 미확인 범위다. 관련 코드와 V-ID를 연결한다.
5. **선택한 방법의 가장 중요한 한계나 부작용은 무엇이며, 어떤 대안이나 대리지표를 고려했는가?**  
   답변 포인트는 한계가 생기는 조건과 영향, 적용하거나 검토한 대안과 전환 조건이다. 대리지표를 썼다면 원래 목표와의 관계를 설명하고 D/V-ID를 연결한다.
6. **과정 중 사용자가 내린 판단이나 개입이 결과를 어떻게 바꿨으며, 그 근거는 어디에서 확인하는가?**  
   답변 포인트는 실제 결정 계기 → 사용자 판단과 AI 역할 → 결과·검증 변화다. PLAN·DECISIONS·REVIEW 중 해당 위치를 정확히 연결한다.

## [현재 결과와 읽는 순서]

현재 구현/미완료/미확인 범위, 설명 대상 코드·자료의 실제 버전/위치, 관련 PLAN·DECISIONS·REVIEW·사용법·과제 지정 문서 위치를 둔다. 코드를 확인하지 않은 계획을 완성본처럼 설명하지 않는다.

## [과제 목적과 성공 기준]

누가 어떤 문제를 해결하고 이 결과로 무엇을 판단/실행하는가. 고정 필수조건, 사용자 선호/절충, 확인 사실과 가정은 무엇인가. 해당 R/Q/U-ID와 출처를 연결한다. 구현 우선순위와 결과 성공 판정을 구별한다.

## [주요 사용자 시나리오와 데이터 흐름]

대표 입력→사용자 행동→주요 처리→저장/출력→사용자가 확인하는 결과를 역할별로 설명한다. 중요한 필드·단위·기간·예외 때의 동작과 실제 파일/함수를 연결한다. 이미 있는 사용법의 버튼 절차 전체를 복제하지 않는다.

## [핵심 방법과 선택 이유]

실제 알고리즘/핵심 처리의 단계와 작은 예를 설명한다. 왜 현재 목표·제약·규모·시간에 이 방법을 골랐는가. 다른 후보의 손익과 버린 이유, 보장 수준, 부작용과 다시 선택해야 할 조건은 무엇인가. 최적화가 아니면 없는 목적함수를 만들지 않고 실제 설계 선택을 설명한다.

가능해 후보별 같은 필수조건 충족 근거와 동일 입력의 실제 지표·단위·차이·검증 위치를 설명한다. 후보를 둘 등으로 줄였다면 실제 이유도 보존한다. 단순 추천이나 알고리즘 이름 대신 정량 근거로 선택을 따라갈 수 있게 한다. 미측정 수치를 꾸미지 않는다.

## [주요 검증 — 왜 믿을 수 있는가]

핵심 검증별로 구분한다.

- [사유] 어떤 잘못된 결과/상태를 막거나 구별하려 했는가.
- [방법] 어떤 입력과 순서로 무엇을 대조했는가.
- [신뢰 근거] 기대값이 어디서 왔고 생산 구현과 무엇이 독립/공유인가. 이 방식이 어떤 오류를 찾을 수 있는가.
- [실제 결과] 기대와 관측이 어떻게 같거나 달랐으며 최종적으로 무엇을 확인했는가.
- [한계] 무엇을 입증하지 못했고 현재 코드/입력에 여전히 유효한가.
- [근거] V-ID와 실제 실행/파일 위치. 전체 로그는 REVIEW 정본을 본다.

‘3명이 리뷰함’, ‘N개 통과’만으로 타당성을 대신하지 않는다. UI/실행/문서/사람 확인과 계산의 독립성을 구분한다.

## [큰 수행 과정과 방향 전환]

본문의 수행 과정은 실제 작업 순서대로 설명한다. 작업 중에는 실제 사건이 생길 때 해당 절을 갱신하고, 최종본에서 사건의 시간순과 현재 결과를 대조한다. 예시 흐름을 실제 이력으로 꾸미지 않는다. 자료 해석→질문/답→기준/방향→후보/선택→첫 구현→문제 발견/개선→다음 구현/검증 중 실제 발생한 사건의 이유와 결과를 Q/D/V 또는 파일 위치로 연결한다. 모든 명령·대화의 복사본은 만들지 않는다.

## [어려운 사례와 경계조건]

실제 겪은 어려움은 관측 증상→가능 원인/가정→선택한 처리→수정/재검증→남은 영향으로 설명한다. 경계 입력을 실제 실행한 것, 코드로만 살핀 것, 아직 잠재 위험인 것을 구별한다. 어려움을 겪지 않았다면 사건을 만들어 넣지 않는다.

## [한계·대안·대리지표]

실제 한계의 원인과 사용자/결과에 미치는 영향, 채택 또는 검토만 한 대안, 바꿀 조건을 설명한다. 대리지표를 썼다면 원래 확인하려던 값, 직접 얻지 못한 이유, 사용한 값·가정·편향/오해 위험을 적는다. 사용하지 않았다면 그 사실만 밝힌다. 일반적인 미래 기능 목록으로 채우지 않는다.

## [사용자와 AI의 판단·개선]

AI가 구현한 것, 사용자가 지시/승인한 것, 사용자 직접 수정, 위임 범위의 AI 판단을 구별한다. 중요한 수용·수정·거절/추가 의견은 제안→실제 의견/이유→반영/보류→영향/검증 순서로 실제 근거를 연결한다. 이유 미기록은 확인 필요, 개입 미기록은 기록 없음으로 둔다.

## [과제 지정 AI 협업 문항 대응]

실제 원문의 문항별로 질문 원문/출처, 관련 사실과 과정, 근거 위치, 미완/미확인을 정리한다. 문항 수/정확한 표현을 이전 과제의 복기에서 추정하지 않는다. 원문이 없으면 미제공으로 표시한다. 이 절에는 지정 AI 협업 문서에 필요한 실제 사실과 근거를 연결한다. 사전 복기용 예상 문항과 답변 핵심은 상단의 별도 절에서 찾는다.
